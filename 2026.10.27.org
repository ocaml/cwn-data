* uniker.nl - Unikernels in OCaml
:PROPERTIES:
:CUSTOM_ID: 1
:END:
Archive: https://discuss.ocaml.org/t/ann-uniker-nl-unikernels-in-ocaml/18625/1

** Calascibetta Romain announced


We are delighted to announce the launch of our new website: [[https://uniker.nl/][uniker.nl]]. This website embodies our new approach to developing unikernels with OCaml 5. It offers a new way of developing unikernels and now places just as much emphasis on the deployment and use of unikernels. The website features a comprehensive [[https://uniker.nl/introduction/][tutorial]] and resources to help you get to grips with our new ecosystem, providing a _first entry point_ for anyone interested in unikernels in OCaml.

The content of this site is available [[https://github.com/robur-coop/uniker.nl][here]], is powered by the excellent [[https://yocaml.github.io/tutorial/index.html][YOCaml]] project, and is deployed using our [[https://github.com/dinosaure/immuable][immuable]] unikernel.

*** Our new ecosystem

We were able to present our new workflow at the [[https://ocaml.org/ocaml-workshop-2026][OCaml Workshop 2026]] ([[https://docs.google.com/presentation/d/1bOXJAPEEjPBx_8i0frThKhLpHd8C7-EPRczEQjvz6JU/edit?slide=id.g3f7268904c5_0_1#slide=id.g3f7268904c5_0_1][slides]]) and our approach can be summarised in two main points:
- the development of unikernels
- the deployment of unikernels and their uses

**** To develop unikernels

Our co-operative has been developing unikernels for quite a few years now. [[https://blog.robur.coop/][Our blog]] showcases some of the ones we use for our infrastructure. Based on our experience, we are well aware of the constraints and limitations of what we can achieve when it comes to developing an application in the form of a unikernel. The best-known constraint we have accepted is not to require the POSIX interface (nor to attempt to replicate it) in terms of protocols and formats. One of the rules still adhered to today is, amongst other things, [[https://discuss.ocaml.org/t/on-concurrency-models/15899/13][not to depend on I/O or a scheduler]][[https://discuss.ocaml.org/t/why-ocsigen-is-staying-on-lwt-for-now/18318/27][1]] when providing implementations.

Building on this experience, we have been able to develop protocols and formats that are currently being used by others in contexts other than unikernels.

However, we have also seen the limits of what we can achieve, particularly with what MirageOS currently offers. With this in mind, and upon further reflection on the constraints we face when developing unikernels (particularly regarding cross-compilation), we have decided to structure the development of unikernels using two tools: [~unic~](how to infer dependencies and _vendor_ them) and [~mfetch~](how to vendor dependencies).

**** [[https://github.com/robur-coop/unic][~unic~]]: how to infer dependencies and _vendor_ them

One constraint we face with unikernels is the need to recompile C files with specific options so that they do not depend on what already exists on the host system. The approach taken by MirageOS 3 was to distribute the result of this specific compilation within libraries that contain C stubs (such as [[https://github.com/mirage/digestif][~digestif~]] or [[https://github.com/mirage/mirage-crypto][~mirage-crypto~]]). The problem is that we were forcing users of these libraries to install [[https://github.com/mirage/ocaml-solo5][~ocaml-solo5~]] in order to obtain a compilation environment for C files specific to [[https://github.com/solo5/solo5][Solo5]], our core component for producing unikernels.

MirageOS 4 then arrived with ~dune~ and its contexts, allowing us to achieve a consistent compilation environment for C files. However, this approach introduced new a constraint: all dependencies of our unikernels had to use ~dune~, which is *legitimately* not the case in the OCaml ecosystem.

It is for this reason that we decided to refine the need to recompile some of our libraries a little further and, finally, to be able to capitalise on a key advantage of [[https://github.com/mirage/ocaml-solo5][~ocaml-solo5~]], namely that compiling OCaml files with this compiler produces exactly the same result as if you were using your host OCaml compiler: in other words, and as has been the case from the beginning, we strictly only need to cross-compile the C files.

It is therefore at the intersection of these two features (only needing to cross-compile the C files and being able to reuse libraries written in pure OCaml and compiled with the host compiler) that we can offer users the ability to write this sort of code without involving any maintenance work on libraries that do not use ~dune~ and without necessarily having to recompile everything:

#+begin_src shell
$ opam install unic
$ cat >main.ml<<EOF
> open Digestif

> let () = Mkernel.run [] @@ fun () ->
>   Fmt.pr "%a\n%!" SHA1.pp (SHA1.digest_string "Hello World!")
> EOF
$ unic infer -r .
Module Digestif is provided by several ocamlfind packages:
  [0] digestif.c
  [1] digestif.ocaml
Pick one [0-1]: 0
digestif
mkernel
$ opam source digestif
$ opam source mkernel
$ dune build
$ solo5-hvt -- _build/solo5/main.exe --solo5:quiet
2ef7bde608ce5404e97d5f042f95f89f1c232871Solo5
#+end_src

~unic~ is therefore a tool capable of inferring the dependencies of an OCaml project without using a specific build system, and of calculating what needs to be cross-compiled (in this case ~digestif~ and ~mkernel~ but not ~fmt~) to produce a unikernel. The project serves our purpose first and foremost, but it is worth noting that it can also be useful when compiling statically linked
executables.

This tool offers a whole range of sub-tools for analysing META files, viewing an artefact from different perspectives (its module name, its ~ocamlfind~ package name and its OPAM package name) or analysing OCaml artefacts (such as ~*.cmxa~ files).

We would particularly like to thank @Octachron for his [[https://github.com/Octachron/codept][~codept~]] project (on which ~unic~ is based) and for working with us to improve it.

**** [[https://github.com/robur-coop/mfetch][~mfetch~]]: how to vendor dependencies

Having identified more precisely which dependencies need to be cross-compiled, we now need to download these dependencies. Although ~opam source~ does the job very well, we wanted a tool that could download the source code from various types of source, such as:
- from a _tarball_, as is usually the case
- but also from a Git repository
- or even from a specific location on your file system

That is why we developed ~mfetch~, which allows you to download software sources based on information provided by OPAM or the user, and to create a ~vendors~ folder containing all these sources.

#+begin_src shell
$ unic infer -r . -o _mfetch
$ mfetch --with-dune-file
 digestif                 │██████████████████│    3.1 MiB /    3.1 MiB    5.9 MiB/s 
 mkernel                  │██████████████████│   37.3 KiB /   37.3 KiB    3.4 MiB/s 

digestif                         ok
mkernel                          ok
$ dune build
#+end_src

~mfetch~ also allows you to check whether you have modified any of the source files (for a bug fix) or to generate a ~*.locked~ file so that you can then verify the reproducibility of your unikernel using our other tool [[https://github.com/robur-coop/orb][~orb~]]. The tool itself is not revolutionary, but it helps to streamline the workflow.

#+begin_src shell
$ mfetch status
digestif                         ok
mkernel                          ok
$ mfetch lock
2 sources locked into _mfetch.locked
#+end_src

**** Libraries for OCaml 5

Our new workflow now uses OCaml 5. As well as updating the basic building blocks required to produce unikernels with OCaml 5, we have also developed a series of libraries that primarily enable us to take advantage of effects. Furthermore, over the past several years we have developed:
- [[https://discuss.ocaml.org/t/ann-miou-a-simple-scheduler-for-ocaml-5/12963][Miou]], our scheduler for OCaml 5
- [[https://github.com/robur-coop/mkernel][~mkernel~]], a derivative of our Miou scheduler designed to handle the I/O provided by Solo5
- [[https://discuss.ocaml.org/t/ann-mnet-a-new-tcp-ip-stack-for-unikernels-in-ocaml/17851][~mnet~]], a reimplementation of the TCP/IP stack (using [[https://github.com/robur-coop/utcp][~utcp~]]) in OCaml with effects
- and plenty of other libraries such as [[https://github.com/robur-coop/mhttp][~mhttp~]], [[https://github.com/robur-coop/colombe][~msendmail~]], [[https://github.com/robur-coop/mfat][~mfat~]], [[https://github.com/robur-coop/vif][~vifu~]], etc.

These libraries, currently used by some of our deployed unikernels, allow us to offer developers a _direct-style_ approach to implementing their unikernels.

But what is key to take away from this emerging ecosystem is the retrospective analysis of past projects to ensure we do not repeat the same mistakes. We very quickly realised that it could be very difficult to migrate existing libraries using [[https://github.com/ocsigen/lwt][~lwt~]] (the MirageOS scheduler) to Miou (or any other scheduler using effects). We therefore took the opportunity not only to propose a _direct-style_ approach using Miou, but also to rethink the implementation of our libraries in light of what we've learnt from deploying unikernels with MirageOS. We have paid particular attention to memory usage, to avoiding known CVEs from our previous implementations (as we are also part of the OCaml security team), and also to offering an alternative API that does not systematically rely on functors.

The approach is still experimental, as we need to consolidate this new ecosystem across several layers, but we are firmly convinced (based on what we've observed in our deployed unikernels) that these new implementations are significantly better than what we used in the past.

**** To deploy unikernels

The other side of unikernels is deployment. Indeed, it is not just a matter of developing unikernels (and making their development easier) but also of deploying and using them. Our main objective remains to replace existing services with unikernels (name servers, websites, time servers, etc.), and the way to compete with existing infrastructure is to actively deploy and use our unikernels.

That is why we have developed two projects:
- [[https://github.com/robur-coop/albatross][Albatross]], an OCaml service for launching unikernels
- [[https://github.com/robur-coop/aussi][Aussi]], an OCI runtime for Solo5

We mainly use Albatross in conjunction with our infrastructure for verifying the reproducibility of our unikernels: [[https://builds.robur.coop][builds.robur.coop]]. In this way, we can trace the dependencies of the unikernels - particularly their CVEs - and ensure supply-chain security.

Next comes deployment, and we are therefore seeking to integrate our unikernels into existing infrastructure and provide ways of monitoring them, in particular using [[https://www.influxdata.com/][InfluxDB]], [[https://www.influxdata.com/time-series-platform/telegraf/][Telegraf]] and [[https://grafana.com/][Grafana]].

This is how we are able to offer services such as (note that some haven't yet been ported to ~mkernel~/~mnet~, but will be soon):
- simple websites such as our https://blog.robur.coop/ (using [[https://github.com/robur-coop/unipi][~unipi~]] or [[https://github.com/dinosaure/immuable][~immuable~]])
- domain name management for domains such as ~robur.coop~, ~reyn.ir~ or ~din.osau.re~ (via our [[https://github.com/robur-coop/dns-primary-git/][primary]] DNS server and [[https://git.robur.coop/robur/dns-secondary/][secondary]] server)
- a VPN service, whether using [[https://github.com/robur-coop/miragevpn][MirageVPN]] or [[https://github.com/robur-coop/zostera][Zostera]]
- a time server (using [[https://github.com/robur-coop/chaos][Chaos]]): https://chaos.osau.re/
- a [[https://github.com/robur-coop/caldav][CalDAV]] calendar system
- [[https://mailingl.st][a mailing list]] using the [[https://github.com/robur-coop/ptt][~ptt~]] project
- a TLS termination proxy such as [[https://github.com/robur-coop/tlstunnel][~tlstunnel~]] or [[https://github.com/robur-coop/contruno][~contruno~]] (used by sherlocode.com)
- and many more!

It is therefore through actual use that we improve our unikernels and the libraries that depend on them. That is why part of our tutorial also focuses on deploying unikernels, so that you can use them and help us with your feedback.

Finally, we are also proposing a project called [[https://mollymawk.robur.coop/][Mollymawk]], designed to simplify the deployment of unikernels via a web interface, so that, in future, we can offer access to our infrastructure to anyone who wishes to use it (and we would like to thank @kit-ty-kate for their various attempts).

*** Unikernels and MirageOS

Enthusiasts may wonder what the advantage of our approach is compared to MirageOS, a unikernel project that remains active thanks to our maintenance work. Our approach is characterised by five points that we have identified as glass ceilings to the adoption of unikernels:
- the first concerns the use of [[https://github.com/mirage/ocaml-cstruct][~ocaml-cstruct~]]. The fundamental issue remains the use of ~bigarray~ as _buffer_ instead of ~bytes~/~string~. Our experience whilst developing [[https://github.com/robur-coop/miragevpn][MirageVPN]] has shown us that using ~cstruct~ as a systematic library for the _buffer_ concept across our entire ecosystem was our biggest *penalty* in terms of throughput for our unikernel. This is why we decided not only to develop [[https://github.com/robur-coop/bstr][~bstr~]] and [[https://github.com/robur-coop/bstr][~slice~]], but also to rewrite the majority of our libraries by replacing ~cstruct~ with ~bytes~/~string~ (this was the case for [[https://github.com/mirleft/ocaml-tls/pull/497][~ocaml-tls~]], [[https://github.com/mirage/mirage-crypto/pull/214][~mirage-crypto~]], [[https://github.com/mirage/ocaml-dns/pull/351][~ocaml-dns~]] and, more recently, [[https://github.com/mirage/awa-ssh/pull/85][~awa-ssh~]] and [[https://github.com/robur-coop/utcp/pull/55][~utcp~]]). The conclusion is quite simple: it is not a question of stopping using bigarray, but rather of not making their use systematic in our APIs.
- the second point concerns the use of functors to express the devices required by the unikernel. The approach of reusing interfaces to inject specific implementations that concretize these devices via functors may seem appealing, but the maintenance cost of such an ecosystem—constrained by interfaces that are no longer really up to date with new concepts—has led us into [[https://github.com/robur-coop/dnsvizor/blob/83b32596c4a08c080067e1cd36fe5788b90cdd78/unikernel.ml#L610-L631][absurd situations]] whenever we've needed to develop more specific unikernels tailored to our requirements. Once again, the rule is not to stop using functors, but not to make their use systematic.
- the third point concerns the compilation of unikernels. MirageOS relies on a workaround that, even today, integrates very poorly with ~dune~; this can be defined as: _multi-stage compilation_, where a code-generation phase is required depending on the desired _target_. This way of structuring the workflow with a set of dependencies dictated by the tool explicitly restricts the developer in what they wish to do and how they wish to do it. Although there are constraints on compiling a unikernel (such as not using the ~Unix~ module), our cooperative has decided to provide *informative* (and not prescriptive) tools that assist (but do not force) the user in designing their unikernel (furthermore, we are also delighted to introduce [[https://github.com/robur-coop/unic][~unic~]] and [[https://github.com/robur-coop/mfetch][~mfetch~]]). The key point of our new approach is to ensure that it is the user who has the final say, rather than the tool (in this case, ~mirage~), in the development of unikernels.
  
  It is very intricate on what the ~mirage~ tool does, including generation of functor applications and some initialization stubs, as well as opam version constraints (since the functors and initialization functions may change in new opam packages). The ~mirage~ tool has a closed world assumption, and it is hard to use a package not known by ~mirage~ - it is as well very hard to use ~js_of_ocaml~ in a ~mirage~ unikernel.
- the fourth point concerns the maintenance of this ecosystem, and specifically the maintenance of the tools and libraries on which MirageOS relies. Furthermore, we have experienced some disappointments with ~opam-monorepo~, and we are finding, day by day, that it is becoming increasingly difficult to update ~mirage-tcpip~ in line with OCaml 5. Our involvement in the OCaml security team has also led us to wish to deprecate certain libraries due to a lack of maintenance. We are therefore refocusing our ecosystem on what our co-operative produces and maintains.
- Finally, the last point concerns our work with the community, which remains unchanged despite the emergence of AI. We have observed a certain abusive use of AI to solve non-existent problems relating to unikernels, which, in our view, undermines our credibility regarding the security, maintenance and quality of our software. In this regard, we are trying to distance ourselves from those who prefer _vibe-coding_ rather than deployment. This approach is reflected in our use of the [[https://www.gnu.org/licenses/agpl-3.0.en.html][AGPL]] as our licence (whilst offering the option of dual licensing) and a [[https://github.com/Solo5/solo5/blob/main/AI.md][POLICY]] regarding the use of AI.

All of this has led us to propose MirageOS 5, which represents a fundamental departure from the factors that characterised the failure of MirageOS 4 (for which I was the release manager). It is therefore, having acknowledged this defeat (and analysed it), that we are proposing a new approach to creating and deploying unikernels: [[https://uniker.nl/][uniker.nl]].

As regards the projects associated with the MirageOS project, we will, of course, continue to maintain some of them, whilst at the same time offering more up-to-date solutions to those who use some of our libraries. We would also be delighted to help anyone wishing to migrate to our new libraries and tools; we are (as we always have been) available to assist.
      



* Announcing segmap, a fast data structure for renamings
:PROPERTIES:
:CUSTOM_ID: 2
:END:
Archive: https://discuss.ocaml.org/t/ann-announcing-segmap-a-fast-data-structure-for-renamings/18626/1

** François Pottier announced


Hello! I am happy to announce ~segmap~. This OCaml library implements *segment maps*, a purely functional data structure that represents an increasing function of the natural numbers into the natural numbers. This data structure offers efficient support for many operations, including lookup, reverse lookup, horizontal and vertical displacements, insertion at the front end, composition, meet, and join. This data structure may be useful in proof assistants, compilers, and symbolic computation systems where variables are encoded as de Bruijn indices or co-de Bruijn indices.

The data structure is described in [[https://cambium.inria.fr/~fpottier/publis/fpottier-segmap.pdf][this paper]], and [[https://cambium.inria.fr/~fpottier/segmap/doc/segmap/Segmap/][the documentation of the library]] is available online.

#+begin_example
  opam update
  opam install segmap
#+end_example

Happy hacking,
FP.
      



* hexen.0.1
:PROPERTIES:
:CUSTOM_ID: 3
:END:
Archive: https://discuss.ocaml.org/t/ann-hexen-0-1/18627/1

** Mikhail announced


Yo!

I needed to decode the hexadecimal substring, so I wrote [[https://github.com/dx3mod/hexen][Hexen]], yet another library for encoding and decoding hexadecimal byte sequences.

The main goal of this library is to provide a flexible API for encoding and decoding substrings into any destination (bytes or buffers).

*** Usage

Hexen provides high-level functions like ~encode~ and ~decode~ for quick encoding and decoding of strings or substrings.

#+begin_src ocaml
Hexen.encode "Hello World";;
(* - : string = "48656c6c6f20576f726c64" *)

Hexen.decode "48656c6c6f20576f726c64";;
(* - : string = "Hello World" *)
#+end_src

#+begin_src ocaml
Hexen.encode_substring "Hello World" 0 5;;
(* - : string = "48656c6c6f" *)

Hexen.decode_substring "48656c6c6f20576f726c64" 0 10;;
(* - : string = "Hello" *)
#+end_src

Also, Hexen provides functions to encode and decode strings or substrings directly into existing buffers or bytes.

#+begin_src ocaml
let buffer = Buffer.create 16 in

Hexen.encode_to_buffer "Hello" buffer;
Hexen.encode_substring_to_buffer "Hello World" 5 6 buffer;

let bytes = Bytes.create 12 in 
Hexen.decode_into (Buffer.contents buffer) 0 bytes 0 22;
Bytes.set bytes 11 '!';

bytes
(* - : bytes = Bytes.of_string "Hello World!" *)
#+end_src
      



* intel_hex.1.0
:PROPERTIES:
:CUSTOM_ID: 4
:END:
Archive: https://discuss.ocaml.org/t/ann-intel-hex-1-0/18628/1

** Mikhail announced


Yo!

I am happy to announce the first major release of the [[https://github.com/dx3mod/intel_hex][Intel HEX manipulation library]].

Intel HEX format is commonly used to represent compiled program code and data that is loaded into a microcontroller, flash memory, or ROM in embedded systems programming.

And now you can work with it in pure OCaml!

*** Changes

- Redesign API;
- Added ~Memory~ module to process memory images of your firmwares;
- Instead of using the ~ohex~ package, we start use [[https://discuss.ocaml.org/t/ann-hexen-0-1/18627/1][hexen]] for encoding and decoding hexadecimals;

*** In use

The library provides a simple API for parsing and creating Intel HEX files. To create an Intel HEX file, you can use the following code:
#+begin_src ocaml
Intel_hex.Record.
[
  Extended_linear_address 0x0F;
  Data (0x0000, "Hello ");
  Data (0x0007, "World!");
  End_of_file;
]
|> Intel_hex.Object.to_string
|> print_endline
#+end_src
#+begin_example
:02000004000FEB
:0600000048656C6C6F20E6
:06000700576F726C6421CA
:00000001FF
#+end_example

And to parse a string containing an Intel HEX file:

#+begin_src ocaml
":0600000048656C6C6F20E6\n:06000700576F726C6421CA"
|> Intel_hex.Object.of_string
(* - : Intel_hex.Object.t =
  [ Intel_hex.Record.Data (0, "Hello "); 
    Intel_hex.Record.Data (7, "World!") ] *)
#+end_src

However, the library also provides a module for working with memory images built from Intel HEX files or other sources.

#+begin_src ocaml
Intel_hex.Memory.of_string ~block_size:6 "Hello World!"
(* - : Intel_hex.Memory.t =
 [ Intel_hex.Memory.Segment(0x0000, "Hello ");
   Intel_hex.Memory.Segment(0x0006, "World!") ] *)
#+end_src

For more details, see the [[https://ocaml.org/p/intel_hex/latest/doc/index.html][API reference]].

** Hhugo announced


I'm pleased to announce the joint release of js_of_ocaml and wasm_of_ocaml 6.5.0, compilers from OCaml bytecode to JavaScript and WebAssembly.

This release brings together more than 130 pull requests (about 400 commits) from 7 contributors since 6.4.0. Highlights:

- *OCaml 5.6* support.
- *OxCaml*: improved support.
- *Introcaml*: experimental support for [[https://discuss.ocaml.org/t/ann-introcaml-alpha-polymorphic-printing-and-introspection-for-ocaml/18407][Introcaml]] (OCaml values shown in OCaml syntax in Chrome DevTools).
- *Faster compilation*: about 25–30% faster on large programs.
- *Smaller output*: binary constants are emitted as base64 and the generated JavaScript is tighter (the toplevel example goes from 13.6 MB to 9.0 MB).
- *wasm_of_ocaml*: BLAKE2 and zstd (~Digest.BLAKE2*~, compressed marshaled values) no longer require multi-memory support, so they work in Safari; plus faster runtime primitives and better sourcemaps.
- *Effects*: better code with ~--effects=cps~ and ~--effects=double-translation~
- *New web API bindings*: WebGL2, Web Crypto, Service Workers, Clipboard, Notification, FontFace, and more. The toplevel can run in a Web Worker.
- Many bug fixes ...

Breaking changes: ~js_of_ocaml-lwt.logger~ is removed (~lwt_log~ is deprecated), the ~Typed_array.float{32,64}Array_fromArray~ signatures changed.

Contributors to this release: Vincent Balat, Frédéric Bour, Shon Feder, habakan, Hugo Heuzard, Robin Ricard and Jérôme Vouillon. Thank you all!

See the [[https://ocsigen.org/js_of_ocaml/][documentation]] and the [[https://github.com/ocsigen/js_of_ocaml/blob/master/CHANGES.md][full changelog]]. Please report any issue on [[https://github.com/ocsigen/js_of_ocaml/issues][GitHub]].

It should soon be avaible on opam (https://github.com/ocaml/opam-repository/pull/30987)

** Ridwan Adebosin announced


Hi everyone,

I've been building *TIFF Inspector*, a tool for looking inside TIFF files
(directories, tags, storage layout, samples and planes), built on
[[https://github.com/geocaml/ocaml-tiff][geocaml/ocaml-tiff]].

- Live: https://tiff-inspector.onrender.com/
- Code: https://github.com/RidwanAdebosin/tiff-inspect (MIT)

It comes as a CLI, an HTTP API and a web UI. Every reported value says where it
came from: read from the file, a spec default, or absent. Nothing is guessed.

*** What might interest OCaml folks

* ocaml-emcc: compile OCaml programs with their C stubs to WebAssembly
:PROPERTIES:
:CUSTOM_ID: 10
:END:
Archive: https://discuss.ocaml.org/t/ann-ocaml-emcc-compile-ocaml-programs-with-their-c-stubs-to-webassembly/18649/1

** rboud announced


Hi everyone,

I've been working on a tool called ocaml-emcc, and it's now in a state where other people could try it: https://github.com/rboudrouss/ocaml-emcc

The idea is pretty simple. Instead of compiling OCaml to JS or wasm, I compile ~ocamlrun~ with emscripten, compile all the C stubs of the program and its dependencies with emcc, and link the whole thing into one module. Nothing has to be rewritten in JavaScript. zarith, sqlite3, camlzip, cryptokit, mirage-crypto, ctypes bindings and so on "just" work, and so does your own C.

The obvious downside is that it's bytecode running in an interpreter, so it's a lot slower than js_of_ocaml or wasm_of_ocaml. If your code is pure OCaml or its C stubs already have JavaScript implementations, use those instead. This is for the cases where the FFI part is the problem.

Give it a shot!

#+begin_example
opam pin add ocaml-emcc git+https://github.com/rboudrouss/ocaml-emcc.git
source /path/to/emsdk/emsdk_env.sh  # emcc in PATH (you need to install emscripten)
ocaml-emcc build main.js     # in your dune project
node main.js                 # or load main.js in a web page
#+end_example

The extension of the output decides what you get (see the README and emscripten's documentation for more flags):

- ~main.js~: node and browsers
- ~main.html~: the same, plus a minimal page
- ~main.wasm~: a standalone module, which still imports a few emscripten functions
- ~main.wasm --wasi~: imports only WASI functions, so it runs on wasmtime or node's WASI

It's still a prototype, so there are rough edges, if you try it on something and it breaks, I'd really like to hear about it. Packages that don't build are exactly what I'm looking for right now. Feel free to propose/ask for new recipes too.

This started as an attempt to compile [[https://gitlab.com/mopsa/mopsa-analyzer][MOPSA]], a static analyzer written in OCaml, to wasm. It turned out to be really hard because of how much FFI it relies on (apron, gmp, clang's frontend…). I eventually got it [[https://mopsawasm.rboud.com][working]] by patching both OCaml and MOPSA's sources, and gave a talk about it at the [[https://ocaml.org/ocaml-workshop-2026/schedule][OCaml Workshop 2026]]. Since then I've been turning that work into a general tool, and it turns out to generalize quite well, so here it is.

I'm curious to hear what people would use it for, especially if you have an OCaml project that never made it to the browser because of its C dependencies.

* stele 0.1.0: syntax-error messages for Menhir grammars
:PROPERTIES:
:CUSTOM_ID: 13
:END:
Archive: https://discuss.ocaml.org/t/ann-stele-0-1-0-syntax-error-messages-for-menhir-grammars/18657/1

** Jérôme Vouillon announced


I'm happy to announce the first release of [[https://github.com/vouillon/stele][stele]], a tool that writes the syntax-error messages of a Menhir grammar for you.

A Menhir parser that meets bad input raises ~Error~, which says where the parse failed but not why. Menhir can show a real message instead, but only if you write one for every error state (every point where the parse can get stuck). A realistic grammar has hundreds of them, and they go stale as the grammar changes.

stele generates them at build time, from ~menhir --list-errors~ and the grammar's ~.cmly~. With a few aliases and one ~%on_error_reduce~ annotation, the calculator from the tutorial reports:

#+begin_example
Error: Assuming that the statements are complete, expecting '}'.
 --> stray.calc:1:6
1 | { 1; ) }
  ·      ^
  ·   ^^ these statements
  · ^ This '{' opens the enclosing construct.
#+end_example

What you get:

- *A message for every error state*, saying what could come next. Each list is checked against the parser's tables, so a message never offers a token the parser would reject in that state.
- *Location hints*: the opening delimiter the input is still inside, and the construct the parser assumed complete. A small runtime library, ~stele.runtime~, turns these into source spans when the parser fails. It depends only on ~menhirLib~, so it works under js_of_ocaml and wasm_of_ocaml. stele leaves the rendering to you; [[https://github.com/johnyob/grace][Grace]] works well.
- *Better wording when you want it*: a small config file gives readable names and groups tokens ("an operator"), and an overrides file holds hand-written messages for the few states that need one. Stale entries in either fail the build.

stele builds on François Pottier's [[https://dl.acm.org/doi/10.1145/2892208.2892224][/Reachability and Error Diagnosis in LR(1) Parsers/]] (CC 2016), the paper behind ~--list-errors~. It automates the work the paper did by hand for CompCert's parser. It started inside the [[https://github.com/ocsigen/wax][Wax]] toolchain, where it produces the error messages of both its grammars.

To try it:

#+begin_example
opam install stele
#+end_example

It needs OCaml ≥ 4.14 and menhir ≥ 20260122. The [[https://github.com/vouillon/stele/blob/main/TUTORIAL.md][tutorial]] takes a small calculator grammar from "Syntax error" to the full setup in ten stages. Its final state is a runnable example to copy.

*Str partial-match stale capture registers underflow*

ANT-2026-KKC4QS4S Str partial-match stale capture registers underflow

~Str.string_partial_match~ records the beginning and end of a captured 
group.
There was an implicit assumption that ~beginning <= end~.
However if it reached the end of the matched string but not the end of 
the regexp, it was possible for the beginning of the group to be matched 
at iteration N of the star operator, and the end of the group to be 
matched at iteration N-1, resulting in ~beginning > end~.
~Str.matched_group~ is safe, it fails with an ~Invalid_argument~ on 
groups with ~beginning > end~, but ~Str.replace_matched~ can crash, 
trying to memcpy ~end - beginning~ bytes.

The example in the ANT is ~ab~ partially matched against ~\(\(a\)b\)+~. 
Group 2 has ~beginning = 2~ and ~end = 1~.

*** Fix

The fix is to record groups with ~beginning > end~ as not matched.

*** Am I affected?

All of the following conditions are necessary:
   * you need to use ~Str.string_partial_match~
     * if you don't use this function you are not affected
   * you need to use one of ~Str.{replace_matched,global_replace,replace_first}~ on the same regexp after a call to ~Str.string_partial_match~.
     * If you use ~Str.group_beginning~ and ~Str.group_end~ and do your own string manipulation that is safe, because the String module would raise on out of bounds accesses. Similarly ~Str.matched_group~ is safe (uses ~String~ functions in its OCaml implementation)
   * the match replacement must reference a group > 0
     * if the replacement string argument is fixed, and doesn't reference any groups, or references only group 0, then you are not affected
   * the referenced replacement group must be under a repetition operator in the original regexp
     * if there is no repetition operator in the regexp, or there are no groups under the repetition operator then you are not affected

For example ~{|\(\(a\)b\)+|}~ as the regular expression in a call to 
~Str.string_partial_match~, followed by a reference to ~\2~ in the 
argument of ~Str.replace_matched~ could be affected.

cleanly or produce a well-formed OCaml object, without corrupting the

causes the Ocaml code to crash or misbehave.

~Filename.quote_command~ returns a quoted command line, suitable for use

ANT-2026-0JXJVEVY

Custom events maintains a cache of user events, it is possible to have a 
corrupt stream that has a valid message with one message type (which can 
be custom/unit/span/int) and then has the same event with a different
