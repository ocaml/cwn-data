uniker.nl - Unikernels in OCaml

Archive: https://discuss.ocaml.org/t/ann-uniker-nl-unikernels-in-ocaml/18625/1

Calascibetta Romain announced

We are delighted to announce the launch of our new website: uniker.nl. This website embodies our new approach to developing unikernels with OCaml 5. It offers a new way of developing unikernels and now places just as much emphasis on the deployment and use of unikernels. The website features a comprehensive tutorial and resources to help you get to grips with our new ecosystem, providing a first entry point for anyone interested in unikernels in OCaml.

The content of this site is available here, is powered by the excellent YOCaml project, and is deployed using our immuable unikernel.

Our new ecosystem

We were able to present our new workflow at the OCaml Workshop 2026 (slides) and our approach can be summarised in two main points:

  • the development of unikernels
  • the deployment of unikernels and their uses
  • To develop unikernels

    Our co-operative has been developing unikernels for quite a few years now. Our blog showcases some of the ones we use for our infrastructure. Based on our experience, we are well aware of the constraints and limitations of what we can achieve when it comes to developing an application in the form of a unikernel. The best-known constraint we have accepted is not to require the POSIX interface (nor to attempt to replicate it) in terms of protocols and formats. One of the rules still adhered to today is, amongst other things, not to depend on I/O or a scheduler1 when providing implementations.

    Building on this experience, we have been able to develop protocols and formats that are currently being used by others in contexts other than unikernels.

    However, we have also seen the limits of what we can achieve, particularly with what MirageOS currently offers. With this in mind, and upon further reflection on the constraints we face when developing unikernels (particularly regarding cross-compilation), we have decided to structure the development of unikernels using two tools: [~unic~](how to infer dependencies and vendor them) and [~mfetch~](how to vendor dependencies).

  • unic: how to infer dependencies and vendor them

    One constraint we face with unikernels is the need to recompile C files with specific options so that they do not depend on what already exists on the host system. The approach taken by MirageOS 3 was to distribute the result of this specific compilation within libraries that contain C stubs (such as digestif or mirage-crypto). The problem is that we were forcing users of these libraries to install ocaml-solo5 in order to obtain a compilation environment for C files specific to Solo5, our core component for producing unikernels.

    MirageOS 4 then arrived with dune and its contexts, allowing us to achieve a consistent compilation environment for C files. However, this approach introduced new a constraint: all dependencies of our unikernels had to use dune, which is legitimately not the case in the OCaml ecosystem.

    It is for this reason that we decided to refine the need to recompile some of our libraries a little further and, finally, to be able to capitalise on a key advantage of ocaml-solo5, namely that compiling OCaml files with this compiler produces exactly the same result as if you were using your host OCaml compiler: in other words, and as has been the case from the beginning, we strictly only need to cross-compile the C files.

    It is therefore at the intersection of these two features (only needing to cross-compile the C files and being able to reuse libraries written in pure OCaml and compiled with the host compiler) that we can offer users the ability to write this sort of code without involving any maintenance work on libraries that do not use dune and without necessarily having to recompile everything: 

    $ opam install unic
$ cat >main.ml<<EOF
> open Digestif

> let () = Mkernel.run [] @@ fun () ->
>   Fmt.pr "%a\n%!" SHA1.pp (SHA1.digest_string "Hello World!")
> EOF
$ unic infer -r .
Module Digestif is provided by several ocamlfind packages:
  [0] digestif.c
  [1] digestif.ocaml
Pick one [0-1]: 0
digestif
mkernel
$ opam source digestif
$ opam source mkernel
$ dune build
$ solo5-hvt -- _build/solo5/main.exe --solo5:quiet
2ef7bde608ce5404e97d5f042f95f89f1c232871Solo5

    unic is therefore a tool capable of inferring the dependencies of an OCaml project without using a specific build system, and of calculating what needs to be cross-compiled (in this case digestif and mkernel but not fmt) to produce a unikernel. The project serves our purpose first and foremost, but it is worth noting that it can also be useful when compiling statically linked executables.

    This tool offers a whole range of sub-tools for analysing META files, viewing an artefact from different perspectives (its module name, its ocamlfind package name and its OPAM package name) or analysing OCaml artefacts (such as *.cmxa files).

    We would particularly like to thank @Octachron for his codept project (on which unic is based) and for working with us to improve it.

  • mfetch: how to vendor dependencies

    Having identified more precisely which dependencies need to be cross-compiled, we now need to download these dependencies. Although opam source does the job very well, we wanted a tool that could download the source code from various types of source, such as:

    • from a tarball, as is usually the case
    • but also from a Git repository
    • or even from a specific location on your file system

    That is why we developed mfetch, which allows you to download software sources based on information provided by OPAM or the user, and to create a vendors folder containing all these sources. 

    $ unic infer -r . -o _mfetch
$ mfetch --with-dune-file
 digestif                 │██████████████████│    3.1 MiB /    3.1 MiB    5.9 MiB/s 
 mkernel                  │██████████████████│   37.3 KiB /   37.3 KiB    3.4 MiB/s 

digestif                         ok
mkernel                          ok
$ dune build

    mfetch also allows you to check whether you have modified any of the source files (for a bug fix) or to generate a *.locked file so that you can then verify the reproducibility of your unikernel using our other tool orb. The tool itself is not revolutionary, but it helps to streamline the workflow. 

    $ mfetch status
digestif                         ok
mkernel                          ok
$ mfetch lock
2 sources locked into _mfetch.locked
  • Libraries for OCaml 5

    Our new workflow now uses OCaml 5. As well as updating the basic building blocks required to produce unikernels with OCaml 5, we have also developed a series of libraries that primarily enable us to take advantage of effects. Furthermore, over the past several years we have developed:

    • Miou, our scheduler for OCaml 5
    • mkernel, a derivative of our Miou scheduler designed to handle the I/O provided by Solo5
    • mnet, a reimplementation of the TCP/IP stack (using utcp) in OCaml with effects
    • and plenty of other libraries such as mhttp, msendmail, mfat, vifu, etc.

    These libraries, currently used by some of our deployed unikernels, allow us to offer developers a direct-style approach to implementing their unikernels.

    But what is key to take away from this emerging ecosystem is the retrospective analysis of past projects to ensure we do not repeat the same mistakes. We very quickly realised that it could be very difficult to migrate existing libraries using lwt (the MirageOS scheduler) to Miou (or any other scheduler using effects). We therefore took the opportunity not only to propose a direct-style approach using Miou, but also to rethink the implementation of our libraries in light of what we've learnt from deploying unikernels with MirageOS. We have paid particular attention to memory usage, to avoiding known CVEs from our previous implementations (as we are also part of the OCaml security team), and also to offering an alternative API that does not systematically rely on functors.

    The approach is still experimental, as we need to consolidate this new ecosystem across several layers, but we are firmly convinced (based on what we've observed in our deployed unikernels) that these new implementations are significantly better than what we used in the past.

  • To deploy unikernels

    The other side of unikernels is deployment. Indeed, it is not just a matter of developing unikernels (and making their development easier) but also of deploying and using them. Our main objective remains to replace existing services with unikernels (name servers, websites, time servers, etc.), and the way to compete with existing infrastructure is to actively deploy and use our unikernels.

    That is why we have developed two projects:

    • Albatross, an OCaml service for launching unikernels
    • Aussi, an OCI runtime for Solo5

    We mainly use Albatross in conjunction with our infrastructure for verifying the reproducibility of our unikernels: builds.robur.coop. In this way, we can trace the dependencies of the unikernels - particularly their CVEs - and ensure supply-chain security.

    Next comes deployment, and we are therefore seeking to integrate our unikernels into existing infrastructure and provide ways of monitoring them, in particular using InfluxDB, Telegraf and Grafana.

    This is how we are able to offer services such as (note that some haven't yet been ported to mkernel~/~mnet, but will be soon):

    • simple websites such as our https://blog.robur.coop/ (using unipi or immuable)
    • domain name management for domains such as robur.coop, reyn.ir or din.osau.re (via our primary DNS server and secondary server)
    • a VPN service, whether using MirageVPN or Zostera
    • a time server (using Chaos): https://chaos.osau.re/
    • a CalDAV calendar system
    • a mailing list using the ptt project
    • a TLS termination proxy such as tlstunnel or contruno (used by sherlocode.com)
    • and many more!

    It is therefore through actual use that we improve our unikernels and the libraries that depend on them. That is why part of our tutorial also focuses on deploying unikernels, so that you can use them and help us with your feedback.

    Finally, we are also proposing a project called Mollymawk, designed to simplify the deployment of unikernels via a web interface, so that, in future, we can offer access to our infrastructure to anyone who wishes to use it (and we would like to thank @kit-ty-kate for their various attempts).

About us

Finally, none of this would be possible without our co-operative and the way we organise our work. You can view the details of our finances here. We accept donations and have recently secured funding from NLnet. Private companies such as Ahrefs and Tarides also sponsor our work. We also have partnerships with OCamlPro and the OCaml Foundation. And we contribute to the OCaml ecosystem on a daily basis by working with individuals and companies.

You can find more details on our website. We would like to emphasise that it is thanks to our structure (that of an association) that we are able to carry out this work, and we would like to thank our sponsors.

Unikernels and MirageOS

Enthusiasts may wonder what the advantage of our approach is compared to MirageOS, a unikernel project that remains active thanks to our maintenance work. Our approach is characterised by five points that we have identified as glass ceilings to the adoption of unikernels:

  • the first concerns the use of ocaml-cstruct. The fundamental issue remains the use of bigarray as buffer instead of bytes~/~string. Our experience whilst developing MirageVPN has shown us that using cstruct as a systematic library for the buffer concept across our entire ecosystem was our biggest penalty in terms of throughput for our unikernel. This is why we decided not only to develop bstr and slice, but also to rewrite the majority of our libraries by replacing cstruct with bytes~/~string (this was the case for ocaml-tls, mirage-crypto, ocaml-dns and, more recently, awa-ssh and utcp). The conclusion is quite simple: it is not a question of stopping using bigarray, but rather of not making their use systematic in our APIs.
  • the second point concerns the use of functors to express the devices required by the unikernel. The approach of reusing interfaces to inject specific implementations that concretize these devices via functors may seem appealing, but the maintenance cost of such an ecosystem—constrained by interfaces that are no longer really up to date with new concepts—has led us into absurd situations whenever we've needed to develop more specific unikernels tailored to our requirements. Once again, the rule is not to stop using functors, but not to make their use systematic.

  • the third point concerns the compilation of unikernels. MirageOS relies on a workaround that, even today, integrates very poorly with dune; this can be defined as: multi-stage compilation, where a code-generation phase is required depending on the desired target. This way of structuring the workflow with a set of dependencies dictated by the tool explicitly restricts the developer in what they wish to do and how they wish to do it. Although there are constraints on compiling a unikernel (such as not using the Unix module), our cooperative has decided to provide informative (and not prescriptive) tools that assist (but do not force) the user in designing their unikernel (furthermore, we are also delighted to introduce unic and mfetch). The key point of our new approach is to ensure that it is the user who has the final say, rather than the tool (in this case, mirage), in the development of unikernels.

    It is very intricate on what the mirage tool does, including generation of functor applications and some initialization stubs, as well as opam version constraints (since the functors and initialization functions may change in new opam packages). The mirage tool has a closed world assumption, and it is hard to use a package not known by mirage - it is as well very hard to use js_of_ocaml in a mirage unikernel.

  • the fourth point concerns the maintenance of this ecosystem, and specifically the maintenance of the tools and libraries on which MirageOS relies. Furthermore, we have experienced some disappointments with opam-monorepo, and we are finding, day by day, that it is becoming increasingly difficult to update mirage-tcpip in line with OCaml 5. Our involvement in the OCaml security team has also led us to wish to deprecate certain libraries due to a lack of maintenance. We are therefore refocusing our ecosystem on what our co-operative produces and maintains.
  • Finally, the last point concerns our work with the community, which remains unchanged despite the emergence of AI. We have observed a certain abusive use of AI to solve non-existent problems relating to unikernels, which, in our view, undermines our credibility regarding the security, maintenance and quality of our software. In this regard, we are trying to distance ourselves from those who prefer vibe-coding rather than deployment. This approach is reflected in our use of the AGPL as our licence (whilst offering the option of dual licensing) and a POLICY regarding the use of AI.

All of this has led us to propose MirageOS 5, which represents a fundamental departure from the factors that characterised the failure of MirageOS 4 (for which I was the release manager). It is therefore, having acknowledged this defeat (and analysed it), that we are proposing a new approach to creating and deploying unikernels: uniker.nl.

As regards the projects associated with the MirageOS project, we will, of course, continue to maintain some of them, whilst at the same time offering more up-to-date solutions to those who use some of our libraries. We would also be delighted to help anyone wishing to migrate to our new libraries and tools; we are (as we always have been) available to assist.

Announcing segmap, a fast data structure for renamings

Archive: https://discuss.ocaml.org/t/ann-announcing-segmap-a-fast-data-structure-for-renamings/18626/1

François Pottier announced

Hello! I am happy to announce segmap. This OCaml library implements segment maps, a purely functional data structure that represents an increasing function of the natural numbers into the natural numbers. This data structure offers efficient support for many operations, including lookup, reverse lookup, horizontal and vertical displacements, insertion at the front end, composition, meet, and join. This data structure may be useful in proof assistants, compilers, and symbolic computation systems where variables are encoded as de Bruijn indices or co-de Bruijn indices.

The data structure is described in this paper, and the documentation of the library is available online. 

opam update
opam install segmap

Happy hacking, FP.

hexen.0.1

Archive: https://discuss.ocaml.org/t/ann-hexen-0-1/18627/1

Mikhail announced

Yo!

I needed to decode the hexadecimal substring, so I wrote Hexen, yet another library for encoding and decoding hexadecimal byte sequences.

The main goal of this library is to provide a flexible API for encoding and decoding substrings into any destination (bytes or buffers).

Usage

Hexen provides high-level functions like encode and decode for quick encoding and decoding of strings or substrings. 

Hexen.encode "Hello World";;
(* - : string = "48656c6c6f20576f726c64" *)

Hexen.decode "48656c6c6f20576f726c64";;
(* - : string = "Hello World" *)

Hexen.encode_substring "Hello World" 0 5;;
(* - : string = "48656c6c6f" *)

Hexen.decode_substring "48656c6c6f20576f726c64" 0 10;;
(* - : string = "Hello" *)

Also, Hexen provides functions to encode and decode strings or substrings directly into existing buffers or bytes. 

let buffer = Buffer.create 16 in

Hexen.encode_to_buffer "Hello" buffer;
Hexen.encode_substring_to_buffer "Hello World" 5 6 buffer;

let bytes = Bytes.create 12 in 
Hexen.decode_into (Buffer.contents buffer) 0 bytes 0 22;
Bytes.set bytes 11 '!';

bytes
(* - : bytes = Bytes.of_string "Hello World!" *)

intel_hex.1.0

Archive: https://discuss.ocaml.org/t/ann-intel-hex-1-0/18628/1

Mikhail announced

Yo!

I am happy to announce the first major release of the Intel HEX manipulation library.

Intel HEX format is commonly used to represent compiled program code and data that is loaded into a microcontroller, flash memory, or ROM in embedded systems programming.

And now you can work with it in pure OCaml!

Changes

  • Redesign API;
  • Added Memory module to process memory images of your firmwares;
  • Instead of using the ohex package, we start use hexen for encoding and decoding hexadecimals;

In use

The library provides a simple API for parsing and creating Intel HEX files. To create an Intel HEX file, you can use the following code: 

Intel_hex.Record.
[
  Extended_linear_address 0x0F;
  Data (0x0000, "Hello ");
  Data (0x0007, "World!");
  End_of_file;
]
|> Intel_hex.Object.to_string
|> print_endline

:02000004000FEB
:0600000048656C6C6F20E6
:06000700576F726C6421CA
:00000001FF

And to parse a string containing an Intel HEX file: 

":0600000048656C6C6F20E6\n:06000700576F726C6421CA"
|> Intel_hex.Object.of_string
(* - : Intel_hex.Object.t =
  [ Intel_hex.Record.Data (0, "Hello "); 
    Intel_hex.Record.Data (7, "World!") ] *)

However, the library also provides a module for working with memory images built from Intel HEX files or other sources. 

Intel_hex.Memory.of_string ~block_size:6 "Hello World!"
(* - : Intel_hex.Memory.t =
 [ Intel_hex.Memory.Segment(0x0000, "Hello ");
   Intel_hex.Memory.Segment(0x0006, "World!") ] *)

For more details, see the API reference.

Js_of_ocaml / Wasm_of_ocaml 6.5

Archive: https://discuss.ocaml.org/t/ann-js-of-ocaml-wasm-of-ocaml-6-5/18632/1

Hhugo announced

I'm pleased to announce the joint release of js_of_ocaml and wasm_of_ocaml 6.5.0, compilers from OCaml bytecode to JavaScript and WebAssembly.

This release brings together more than 130 pull requests (about 400 commits) from 7 contributors since 6.4.0. Highlights:

  • OCaml 5.6 support.
  • OxCaml: improved support.
  • Introcaml: experimental support for Introcaml (OCaml values shown in OCaml syntax in Chrome DevTools).
  • Faster compilation: about 25–30% faster on large programs.
  • Smaller output: binary constants are emitted as base64 and the generated JavaScript is tighter (the toplevel example goes from 13.6 MB to 9.0 MB).
  • wasm_of_ocaml: BLAKE2 and zstd (Digest.BLAKE2*, compressed marshaled values) no longer require multi-memory support, so they work in Safari; plus faster runtime primitives and better sourcemaps.
  • Effects: better code with --effects=cps and --effects=double-translation
  • New web API bindings: WebGL2, Web Crypto, Service Workers, Clipboard, Notification, FontFace, and more. The toplevel can run in a Web Worker.
  • Many bug fixes …

Breaking changes: js_of_ocaml-lwt.logger is removed (lwt_log is deprecated), the Typed_array.float{32,64}Array_fromArray signatures changed.

Contributors to this release: Vincent Balat, Frédéric Bour, Shon Feder, habakan, Hugo Heuzard, Robin Ricard and Jérôme Vouillon. Thank you all!

See the documentation and the full changelog. Please report any issue on GitHub.

TIFF Inspector: an ocaml-tiff based inspector, with an in-browser OCaml playground

Archive: https://discuss.ocaml.org/t/tiff-inspector-an-ocaml-tiff-based-inspector-with-an-in-browser-ocaml-playground/18634/1

Ridwan Adebosin announced

Hi everyone,

I've been building TIFF Inspector, a tool for looking inside TIFF files (directories, tags, storage layout, samples and planes), built on geocaml/ocaml-tiff.

  • Live: https://tiff-inspector.onrender.com/
  • Code: https://github.com/RidwanAdebosin/tiff-inspect (MIT)

It comes as a CLI, an HTTP API and a web UI. Every reported value says where it came from: read from the file, a spec default, or absent. Nothing is guessed.

What might interest OCaml folks

ocaml-tiff fixes. Testing on unusual files turned up a few issues, which I fixed in a vendored copy:

  • BigTIFF entries with several small values stored inline (for example BitsPerSample=[8,8,8], as GDAL writes them) were unreadable.
  • Classic TIFF offsets of 2 GiB and above were sign-extended.
  • SampleFormat stored at an offset rather than inline was not read.
  • Entry introspection, so tools can see field types and counts.

Independent test fixtures. There are 21 small TIFFs generated by a separate Python writer that shares no code with the parser, plus golden outputs. They might be useful to ocaml-tiff as a conformance set, if the maintainers want them.

An in-browser playground. At /playground you can write OCaml and run it against ocaml-tiff and the inspector core on sample files, with no install. It's the toplevel compiled with js_of_ocaml (about 1.3 MB gzipped), running in a web worker. ;; is optional, and compile errors are underlined in the editor.

To get there I wrote JavaScript implementations of the C primitives used by bstr and checkseum. I'd be glad to offer them upstream if that's useful.

The server. It uses OCaml 5 with Eio and cohttp-eio. Each upload is inspected in a separate process with time and memory limits, with rate limiting and graceful shutdown. It runs in Docker on a free Render instance.

Feedback welcome

  • Does the JSON report shape work for other geospatial tooling?
  • geocaml maintainers: would you prefer the fixes as one PR or several small ones?
  • Any TIFFs that inspect wrongly. Issues with a sample file are gold.

Thanks for reading!

bytream.0.4

Archive: https://discuss.ocaml.org/t/ann-bytream-0-4/18639/1

Mikhail announced

Yo!

I am happy to announce the next version of the Bytream library, which allows streaming bytes and processing them with low memory allocation. This release includes many important updates.

Changes

  • Now, Bytream for slices uses the Slice library from the Bstr project instead of its own ~buffer, ~offset, ~length labeled tuples, which require OCaml version 5.2 or higher; 

    let of_channel ?(io_buffer_size = 4096) ic =
  let buffer = Bstr.create io_buffer_size in

  let reader () =
    match In_channel.input_bigarray ic buffer 0 io_buffer_size with
    | 0 -> raise End_of_file
    | len -> Slice_bstr.make ~len buffer
  in

  make reader

  • Added bytream.ozstd for Zstandard compression and decompression via the ozstd library; 

    let output_compressed_string out_stream = 
  let out_stream = Bytream_ozstd.Out.make ~compression_level:3 out_stream in 
  Bytream.Out.output_string out_stream "Cras pulvinar sollicitudin nulla quis tempor.";
  Bytream.Out.flush out_stream

let input_decompressed_line in_stream = 
  let in_stream = Bytream_ozstd.In.make in_stream in 
  Bytream.In.input_line in_stream

  • Added bytream.bin for declarative encoding and decoding bytes via the Bin library; 

    type point = { x : int; y : int }

let point = 
  let open Bin in 
  record (fun x y -> { x; y })
  |+ field neint16 (fun t -> t.x)
  |+ field neint16 (fun t -> t.y)
  |> sealr

let _ = 
  (* ... *)
  let p = Bytream_bin.In.input in_stream point in 
  Bytream_bin.Out.output out_stream point { p with y = p.y * 2 }

Credits

I would like to express my special gratitude to Robur Coop for their libraries (Bstr, Slice, Bin, etc.), which are very closely integrated into my projects such as Bytream, ozstd and other. Thanks!

I am pleased to announce the first release of spvec. This small OCaml library implements semi-persistent vectors. In other words, it offers vectors that support just two operations, namely push and get, and that appear to be persistent (immutable), but must be used according to a restricted discipline. Thanks to this restriction, an efficient implementation, based on a mutable vector, is possible. One might say that this library offers mutable vectors disguised as persistent vectors, with a simple and safe API.

Two submodules are offered, Spvec.Safe and Spvec.Unsafe. The safe variant detects misuses of the library at runtime. The unsafe variant is faster, but does not detect misuses; it should be used only if and when the user's code is believed to be correct.

For more details, see the documentation. 

opam update
opam install spvec

ocaml-emcc: compile OCaml programs with their C stubs to WebAssembly

Archive: https://discuss.ocaml.org/t/ann-ocaml-emcc-compile-ocaml-programs-with-their-c-stubs-to-webassembly/18649/1

rboud announced

Hi everyone,

I've been working on a tool called ocaml-emcc, and it's now in a state where other people could try it: https://github.com/rboudrouss/ocaml-emcc

The idea is pretty simple. Instead of compiling OCaml to JS or wasm, I compile ocamlrun with emscripten, compile all the C stubs of the program and its dependencies with emcc, and link the whole thing into one module. Nothing has to be rewritten in JavaScript. zarith, sqlite3, camlzip, cryptokit, mirage-crypto, ctypes bindings and so on "just" work, and so does your own C.

The obvious downside is that it's bytecode running in an interpreter, so it's a lot slower than js_of_ocaml or wasm_of_ocaml. If your code is pure OCaml or its C stubs already have JavaScript implementations, use those instead. This is for the cases where the FFI part is the problem.

Give it a shot! 

opam pin add ocaml-emcc git+https://github.com/rboudrouss/ocaml-emcc.git
source /path/to/emsdk/emsdk_env.sh  # emcc in PATH (you need to install emscripten)
ocaml-emcc build main.js     # in your dune project
node main.js                 # or load main.js in a web page

The extension of the output decides what you get (see the README and emscripten's documentation for more flags):

  • main.js: node and browsers
  • main.html: the same, plus a minimal page
  • main.wasm: a standalone module, which still imports a few emscripten functions
  • main.wasm --wasi: imports only WASI functions, so it runs on wasmtime or node's WASI

It's still a prototype, so there are rough edges, if you try it on something and it breaks, I'd really like to hear about it. Packages that don't build are exactly what I'm looking for right now. Feel free to propose/ask for new recipes too.

This started as an attempt to compile MOPSA, a static analyzer written in OCaml, to wasm. It turned out to be really hard because of how much FFI it relies on (apron, gmp, clang's frontend…). I eventually got it working by patching both OCaml and MOPSA's sources, and gave a talk about it at the OCaml Workshop 2026. Since then I've been turning that work into a general tool, and it turns out to generalize quite well, so here it is.

I'm curious to hear what people would use it for, especially if you have an OCaml project that never made it to the browser because of its C dependencies.

stele 0.1.0: syntax-error messages for Menhir grammars

Archive: https://discuss.ocaml.org/t/ann-stele-0-1-0-syntax-error-messages-for-menhir-grammars/18657/1

Jérôme Vouillon announced

I'm happy to announce the first release of stele, a tool that writes the syntax-error messages of a Menhir grammar for you.

A Menhir parser that meets bad input raises Error, which says where the parse failed but not why. Menhir can show a real message instead, but only if you write one for every error state (every point where the parse can get stuck). A realistic grammar has hundreds of them, and they go stale as the grammar changes.

stele generates them at build time, from menhir --list-errors and the grammar's .cmly. With a few aliases and one %on_error_reduce annotation, the calculator from the tutorial reports: 

Error: Assuming that the statements are complete, expecting '}'.
 --> stray.calc:1:6
1 | { 1; ) }
  ·      ^
  ·   ^^ these statements
  · ^ This '{' opens the enclosing construct.

What you get:

  • A message for every error state, saying what could come next. Each list is checked against the parser's tables, so a message never offers a token the parser would reject in that state.
  • Location hints: the opening delimiter the input is still inside, and the construct the parser assumed complete. A small runtime library, stele.runtime, turns these into source spans when the parser fails. It depends only on menhirLib, so it works under js_of_ocaml and wasm_of_ocaml. stele leaves the rendering to you; Grace works well.
  • Better wording when you want it: a small config file gives readable names and groups tokens ("an operator"), and an overrides file holds hand-written messages for the few states that need one. Stale entries in either fail the build.

stele builds on François Pottier's Reachability and Error Diagnosis in LR(1) Parsers (CC 2016), the paper behind --list-errors. It automates the work the paper did by hand for CompCert's parser. It started inside the Wax toolchain, where it produces the error messages of both its grammars.

To try it: 

opam install stele

It needs OCaml ≥ 4.14 and menhir ≥ 20260122. The tutorial takes a small calculator grammar from "Syntax error" to the full setup in ten stages. Its final state is a runnable example to copy.

Str partial-match stale capture registers underflow

ANT-2026-KKC4QS4S Str partial-match stale capture registers underflow

Str.string_partial_match records the beginning and end of a captured group. There was an implicit assumption that beginning <= end. However if it reached the end of the matched string but not the end of the regexp, it was possible for the beginning of the group to be matched at iteration N of the star operator, and the end of the group to be matched at iteration N-1, resulting in beginning > end. Str.matched_group is safe, it fails with an Invalid_argument on groups with beginning > end, but Str.replace_matched can crash, trying to memcpy end - beginning bytes.

The example in the ANT is ab partially matched against \(\(a\)b\)+. Group 2 has beginning = 2 and end = 1.

Fix

The fix is to record groups with beginning > end as not matched.

Am I affected?

All of the following conditions are necessary:

  • you need to use Str.string_partial_match
    • if you don't use this function you are not affected
  • you need to use one of Str.{replace_matched,global_replace,replace_first} on the same regexp after a call to Str.string_partial_match.
    • If you use Str.group_beginning and Str.group_end and do your own string manipulation that is safe, because the String module would raise on out of bounds accesses. Similarly Str.matched_group is safe (uses String functions in its OCaml implementation)
  • the match replacement must reference a group > 0
    • if the replacement string argument is fixed, and doesn't reference any groups, or references only group 0, then you are not affected
  • the referenced replacement group must be under a repetition operator in the original regexp
    • if there is no repetition operator in the regexp, or there are no groups under the repetition operator then you are not affected

For example {|\(\(a\)b\)+|} as the regular expression in a call to Str.string_partial_match, followed by a reference to \2 in the argument of Str.replace_matched could be affected.
